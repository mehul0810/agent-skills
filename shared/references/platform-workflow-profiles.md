# Platform Workflow Profiles

Use when platform ownership, exploration effort or proof is unclear. The common contract is a truthful, usable artifact within authorized scope; platform details load only when applicable. These profiles are defaults to adapt, not a list of technologies to install.

## Choose The Work, Not A Ceremony

Record a brief working decision: intended artifact, platform, stage, non-negotiable constraints, open hypotheses and smallest next proof. Inline notes suffice for a tiny change. Keep one authoritative artifact; do not create a PRD, issue, milestone or parallel design document merely to fill a template.

- `explore`: answer a named uncertainty with a bounded artifact budget and stop condition. Use enough truthful representative content/assets to expose the uncertain direction. Compare organizing ideas only when direction is genuinely open, not arbitrary palette variants. An authorized isolated prototype is disposable evidence, not production readiness.
- `build`: implement the selected direction in the owning platform, a useful vertical slice before repetition. Revisit hypotheses when observations contradict them. Keep a brief explanation when an alternative is rejected; no compulsory scoring spreadsheet.
- `verify`: test the changed contract against the exact artifact. Separate behavior, visual craft and native authorability/runtime from instruction compliance. Fix observed in-scope defects; label unavailable proof blocked, not passed.
- `ship`: only when requested and authorized, check packaging, supported compatibility, privacy/security, migration/recovery, release identity and exact publication effects. Earlier stage success never authorizes push, deploy, release or store submission.

Stages are selectable and repeatable, not a mandatory ordering. Exact-value fixes may go directly from build to a narrow verification. A supplied approved design skips ideation. Exploration reduces paperwork and breadth, never authorization or truthful-evidence requirements.

Loop's `workflow_stage: explore` packet is deliberately read-only/advisory. If a requested exploration needs a code or artifact mutation, use an explicitly authorized implementation path; do not relabel a mutating command as exploration to bypass dispatch gates. Absent platform/stage fields retain legacy Loop behavior; explicitly select the platform for new non-WordPress work rather than assuming omission is portable.

## Platform Adapters

| Platform | Owning implementation | Smallest useful proof | What not to import |
| --- | --- | --- | --- |
| `wordpress` | Plugin/theme/site specialist; saved blocks, theme tokens or plugin behavior own their real layer | Relevant visitor and author/editor flow on the exact changed build; existing WordPress proof receipts when applicable | A flattened mockup as editable content; unrelated global admin CSS |
| `web` | Existing static/framework app, routes, components and content source | Actual browser render and key interaction at relevant widths; keyboard/focus and asset/network state | Core blocks, WP-CLI, Studio or plugin-release branches without a WordPress boundary |
| `macos` | Existing native project, window/menu/state ownership and supported OS target | Actual app build/run and task in the native window; relevant keyboard, persistence, permissions and recovery | Browser screenshots as native proof; Figma/Pen's “native design” as app execution |
| `game` | Actual engine or browser runtime, simulation/input, camera, scene/assets and save/state boundaries | Playable representative loop; input/restart/failure, meaningful scene at target camera, measured frame/memory behavior | Marketing-page hierarchy as game acceptance; primitive graybox geometry as proof of a requested realistic final scene |
| `other` | Identify the real platform and supported toolchain before execution | Define the observable user task and available runtime; remain explicit about missing capability | Guessing WordPress or browser proof for an unknown platform |

For games, test mechanic uncertainty with a graybox when appropriate, but use a representative asset/lighting/material slice early when visual credibility is the uncertainty. Record source/license and scale/style fit. A nice screenshot is not a playable loop; a working loop is not credible final art. Neither requires paid APIs or new packages by default.

For native apps, verify tool/runtime capability before promising a native test. On a Linux-only worker, run available portable tests and prepare a narrow native check specification; report native execution as unavailable. Do not use the user's machine or sign/package/distribute an app without the relevant authorization. Respect explicit accessibility exclusions; preserve other relevant checks and never mark an excluded check passed.

## Scoped Learning

Keep a lesson with platform, repository/surface, applicable conditions, evidence, confidence and a review trigger. “Use richer scene assets for a realistic game” is not “all admin pages need immersive media.” Store a client convention locally. Repeated wording alone does not prove a general lesson; promote only after counterexamples and independent outcomes support broader applicability. Preserve historical observations and uncertain results rather than rewriting them into proof.
