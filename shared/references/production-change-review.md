# Production Change Review

Use this for a source-aware review of a proposed change in any stack. Start with the intended behavior, exact diff and affected user or operator. Trace a changed decision through its callers, data owner and side effect. Inspect unchanged code where it explains the impact; anchor findings in the change. Apply the relevant project contracts, not a generic claim about "industry standards."

- **Correctness and operations:** What happens on a boundary input, retry, partial failure, or mixed-version rollout? Check the consumers of a changed contract. For a consequential change, ask how the team would detect a failure and recover without damaging data. A copy edit does not need a rollout plan.
- **Security and privacy:** Where does trusted code enforce who may do what to which resource? Authentication alone does not establish ownership or tenant access. Follow sensitive data to storage, output and logs. Prefer the existing authorization and validation primitives. Verify one allowed path and one denied path that leaves no side effect where relevant.
- **Performance:** Count work before guessing time. Trace the hot path's queries, remote calls, allocations and retries at a realistic input size. Distinguish a provable increase in calls from a measured latency or capacity regression. Propose the smallest useful check: assert the call count, compare query plans, or measure the same workload before and after.
- **Modularity and repetition:** Look for two callers that must agree on the *same decision*. If a rule has diverged, name the conflicting outcomes and find its natural owner. Prefer an existing domain function or a small named helper there; test the boundary through both consumers. Keep similar-looking code separate when it serves different contracts. Line count, repetition alone, or preference for a generic utilities layer is not a defect.

Report material findings first: changed file and line, triggering condition, consequence, evidence, smallest compatible fix and how to verify it. Distinguish blockers from follow-ups. Use the project's severity definitions: blocking an unreleased patch is not evidence of a production incident. Label an unmeasured risk as such; do not promote preference or missing evidence to a defect. If nothing material was found, say so and name relevant untested behavior. A review is not a certification, release approval, or permission to edit.

Further reading: [Google's code-review criteria](https://google.github.io/eng-practices/review/reviewer/looking-for.html), [OWASP application security verification](https://owasp.org/www-project-application-security-verification-standard/), and [Google SRE on signals and saturation](https://sre.google/sre-book/monitoring-distributed-systems/).
