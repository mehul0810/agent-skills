# Unity: preserve the project, prove the player

Use this for existing or requested Unity projects. Keep the project's version and conventions unless a requirement makes a change necessary; do not upgrade merely to follow a newer guide. Check documentation for the actual editor, packages and target. For a new project, choose the version, hardware, distribution and visual budget explicitly.

## Establish the working project

Read `ProjectSettings/ProjectVersion.txt`, `Packages/manifest.json` and, when present, `Packages/packages-lock.json`. The manifest describes direct dependencies; the [lock file records the resolved graph](https://docs.unity.com/en-us/engine/6000.6/manual/packages-list/dependencies-lp/upm-conflicts-auto). Check local or Git package sources and platform modules before opening or building. If the pinned editor or source is unavailable, report it rather than silently changing version or regenerating the lock.

Move or rename assets in the Editor, or move each `.meta` file with its asset outside it. Metadata carries the GUID and import settings; losing it can break references. Keep metadata with the source and check for missing references after import. See [Unity's asset metadata guidance](https://docs.unity.com/en-us/engine/6000.0/manual/assets-and-media/import-assets/asset-metadata).

Identify the *active* renderer, not just an installed package: inspect Graphics Settings and the target's Quality levels, overrides, pipeline assets and renderer features. Check the level used in the player. [Unity documents the default and quality override](https://docs.unity3d.com/6000.1/Documentation/Manual/srp-setting-render-pipeline-asset.html); use the equivalent for the pinned version. Built-in, URP, HDRP and custom pipelines have different platform, shader, lighting and performance tradeoffs. Preserve a working pipeline; switching can require material/shader conversion and visual revalidation. For web or phone targets, compare URP and the existing pipeline against HDRP's target support and the actual device budget: Unity 6.0 lists URP and Built-in, but not HDRP, for WebGL, iOS and Android. Check the [comparison](https://docs.unity3d.com/6000.0/Documentation/Manual/render-pipelines-feature-comparison.html) for the pinned version; URP is not automatically right for every project.

## Build the actual loop

Find the startup scene, controls, player controller, camera and completion/recovery path. Make the smallest playable change in their existing architecture; test input, collision, feedback, pause/restart and scene transitions, not just compilation. Use the project's input system and update settings. Physics commonly runs on fixed steps while rendering and input can update at a different cadence. For dynamic input, capture one-shot presses in the appropriate input update or callback and consume them once for physics; do not poll a transient press only in `FixedUpdate` and risk missing or repeating it. Apply Rigidbody forces in the relevant physics step, and test low and high frame rates. The [Input System update mode](https://docs.unity3d.com/Packages/com.unity.inputsystem%401.4/api/UnityEngine.InputSystem.InputSettings.UpdateMode.html) is package-version specific; do not assume dynamic polling is valid in fixed updates, or change the mode without checking all callers.

For Unity 6, inspect the selected **Build Profile**, platform, player settings and effective scene list, including any profile override of global scenes. For older versions use the matching **Build Settings** workflow. Confirm enabled scenes and their order, including the entry scene and every scene reached by the loop; scripted builds can supply their own scene list. See [Build Profiles reference](https://docs.unity3d.com/6000.0/Documentation/Manual/build-profiles-reference.html) and [Unity 2022.3 Build Settings](https://docs.unity3d.com/2022.3/Documentation/Manual/BuildSettings.html). Verify the required [platform build support module](https://docs.unity3d.com/6000.0/Documentation/Manual/building-introduction.html) is installed for that editor. Do not mistake a successful Editor play session or build configuration for a runnable player.

## Validate the delivery boundary

Build the requested native target and launch the resulting player on the relevant OS/device, or state what is unavailable. Keep the complete platform output together. For a browser target, build its supported web platform with the matching module and profile, serve the output over HTTP(S), and play it in the promised browser rather than opening an output file directly. Check load errors, input focus, resize and reload. For compressed builds, inspect server responses for the matching `Content-Encoding`; WebAssembly streaming also needs the appropriate MIME type. See [Unity's server configuration](https://docs.unity3d.com/6000.0/Documentation/Manual/web-server-config-nginx.html). Do not change a shared server or publish a build without authorization.

Measure a representative player on the weakest available target through a cold launch, busiest view and sustained interaction. Record revision, editor, profile, build type, hardware/browser, resolution and quality; report frame-time distribution and hitches, load time and memory where relevant, not average FPS alone. Use a development player and [profiler](https://docs.unity3d.com/6000.0/Documentation/Manual/profiler-profiling-applications.html) to separate CPU, GPU and loading costs, then check the release player because instrumentation changes behavior. If a long frame causes repeated fixed physics steps, investigate both the original stall and physics cost rather than blindly raising the timestep; see [physics performance](https://docs.unity3d.com/6000.0/Documentation/Manual/physics-performance-issues.html).

Two useful boundary tests: (1) a short button press during a long frame is applied once, not lost or duplicated; (2) a clean player launch reaches a later scene and can restart, with the selected profile's scene list and assets intact. Report actual observations separately from untested platforms, missing modules, unavailable devices and any proposed budgets. An Editor view, profiler configuration or generated build alone is not proof of playable delivery.
