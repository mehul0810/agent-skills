# Choose the stack from the game

Start with constraints that can eliminate a candidate: distribution (link, offline install, store or kiosk), weakest supported device/browser and controls, camera freedom, number of active objects, physics/animation needs, and any required networking. Look at the team's existing engine, assets, exporter, skills, license and maintenance budget. A renderer draws frames; it does not necessarily provide a game loop, collisions, input mapping, persistence, or multiplayer.

Record a compact decision: **requirement -> chosen stack -> why the nearest alternative loses -> cheapest test that could change the decision**. Include language, renderer, asset pipeline and only the services the game actually needs. If a stack is explicitly requested, honor it or explain the specific conflict; do not silently replace it. For a genuine unknown, state a provisional assumption and test it rather than producing an engine catalog.

| Requirement that changes the decision | Candidate and tradeoff |
|---|---|
| Fixed-camera browser puzzle, limited download, no install | A DOM or Canvas 2D interaction over licensed photo plates or original prerenders can look photographic. Use a 2D framework such as [Phaser](https://docs.phaser.io/phaser/getting-started/what-is-phaser) if scene management, sprites or physics earn its cost. Flat plates cannot support arbitrary new views or relighting. |
| Authored 2D levels, collisions, controller input and an offline desktop build | An existing Unity 2D project or Godot's editable 2D scenes can save rebuilding a level editor and collision system. Try one edited room and its exported restart with the team's tools. If a single small HTML file is the real deliverable, compare against a simpler web stack rather than assuming an engine export fits. |
| Browser delivery with free inspection, parallax or changing light | A web renderer such as Three.js for a small custom loop, or an engine such as Babylon.js if integrated game systems reduce work. Test the actual browser, input, compressed assets, cold load and memory. If using [WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API), test adapter/device creation and the fallback on the required browser; an API name in a feature list is not support proof. |
| Native desktop or console with close-up characters, dynamic lighting or large traversable scenes | Compare the existing production pipeline against a capable native engine (for example Unreal, Unity or Godot), including animation tooling, streaming and export access. Use [Unreal scalability](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-performance-guide-for-unreal-engine), [Unity pipeline support](https://docs.unity3d.com/Manual/choose-a-render-pipeline.html), or [Godot renderer differences](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html) for the candidate version. A cinematic preset is not a gameplay budget. |
| Mobile or mixed hardware, sustained play, battery or memory limits | Favor a compatible renderer and assets that scale: baked light for static scenery, simpler shaders, texture tiers and fewer transparent layers. Keep near-field silhouettes, contact, controls, and feedback. Test a sustained session on the weakest real device; a desktop window resized to phone dimensions tests layout, not thermals. |

Where two choices remain, build the hardest **representative interaction**, not two whole games. Name the target resolution, frame time (60 fps gives about 16.7 ms per frame), first-load/download limit and memory ceiling where relevant. Distinguish requirements, proposed budgets and measurements. Profile a packaged or served build through motion and the busiest view; report frame-time distribution and hitches, not just average FPS. Separate CPU, GPU and asset-loading costs when diagnosing a miss. On mobile check [frame pacing](https://developer.android.com/games/sdk/frame-pacing) and [sustained performance](https://developer.android.com/games/optimize/adpf). If no viable option meets all hard constraints, present the smallest scope or platform tradeoff for the owner; do not quietly change the style, spend money, or promise unmeasured performance.
