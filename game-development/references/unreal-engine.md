# Unreal Engine 5: identify the build, then prove the game

Use this for a UE5 project or an explicit Unreal feasibility question. It covers work on existing 5.0 through 5.8 projects and the 5.9 preview line, not a claim that every minor or target has been tested. For an existing project, the project's engine is the starting point. For a new one, choose a released version supported by the target SDK, required plugins and team, not the highest number in this guide.

## Identify the engine before opening or saving

- Read the `.uproject` and the project's build/CI pin. `FileVersion` is the descriptor format; `EngineAssociation` may be a launcher minor or an identifier for a team's source build. Resolve the [association to its actual installation](https://dev.epicgames.com/documentation/en-us/unreal-engine/deploying-unreal-engine); don't replace an unfamiliar identifier with the newest launcher version.
- Read that installation's `Engine/Build/Build.version` for major, minor, patch, changelist and branch. For custom builds also record the source revision; for previews confirm the numbered preview from a matching installation manifest, build tag or release record. A folder name or `5.9.0` alone does not distinguish Preview 1, Preview 2 and a final release. If the matching build is absent, report which evidence is missing rather than opening the project in a different editor.
- Check enabled plugins (especially binary-only ones), target platform/toolchain, and any project renderer or input settings the change depends on. Use the documentation selector for the actual minor. A feature described in 5.9 is not a fix for a project pinned to 5.4.

## Keep shipping work separate from an upgrade

As checked **2026-11-24**, Epic has [released 5.8](https://www.unrealengine.com/news/unreal-engine-5-8-is-now-available) and lists [5.9 Preview 2](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-5-9-release-notes), not a production release of 5.9. Recheck the release heading, channel and relevant feature status before applying this distinction to a later build. A stable engine release does not make every experimental feature stable.

For a fix, try the smallest change on the pinned build. For a requested upgrade, capture a baseline package and one repeatable play path. Use a clean source-control snapshot and [Open a Copy](https://dev.epicgames.com/documentation/en-us/unreal-engine/updating-projects-to-newer-versions-of-unreal-engine) or an isolated copy of the project. Verify plugin binaries/source, host SDKs and game targets there before resaving content. Roll back by using the untouched original, not by opening newer [saved assets](https://dev.epicgames.com/documentation/en-us/unreal-engine/versioning-of-assets-and-packages-in-unreal-engine) in the old editor. Compare the same map, inputs, save/load if relevant, and frame times on the same device. A successful conversion alone is not a reason to move the shipping project.

For a 5.9 native experiment, choose a visible problem first. If a retargeted character's hand clips through their chest while reaching into a jacket, compare the existing retarget against the new **Proximity IK** operation on two differently proportioned characters. Inspect contact through the full reach and return in play. This tests a specific animation change; it doesn't justify an engine upgrade by itself.

## Build and check a native slice

1. Use the project's gameplay conventions. In a Blueprint-only exhibition game, for example, connect an input action on the possessed pawn/controller to an interactable, change its state, show or sound the consequence and allow retry. Keep the binding that the project uses (including its active mapping context if it uses Enhanced Input). Use a runtime C++ module for existing native code, needed platform integration or a measured bottleneck; an editor-only module does not ship. Don't add C++ just to make a Blueprint feature look production-ready.
2. For realism, check one close interaction from the player's camera. Compare scale, material response, contact and moving shadows before choosing a rendering feature. If Lumen or Nanite is a candidate, check the pinned version, renderer and device support, and compare a cheaper lighting or geometry tier on the weakest target. A before/after traversal is more useful than a cinematic still.
3. [Package for the target](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project): check the Game Default Map, game mode/pawn, cooked maps and assets (including runtime-loaded references), runtime plugins and platform SDK. For automation, use the matching installation's AutomationTool (`RunUAT.bat` or `RunUAT.sh`); inspect `BuildCookRun -Help` for that build rather than guessing target flags. Keep build, cook, stage and package logs so a missing asset is not misdiagnosed as an input problem.
4. Start the packaged game outside the editor. Play from entry through interaction, consequence and retry with the promised inputs. Record the engine build, package/configuration, device, resolution and scalability tier. Profile the same busy path in a representative packaged build with [Unreal Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-insights-in-unreal-engine); compare CPU/GPU frame times, tail latency and streaming hitches against the target. State separately what ran in Play In Editor (PIE), what packaged, what was played, and what was measured. If a target or toolchain is unavailable, leave its result unverified.

## 5.9 Web: a specific preview experiment

Distinguish a game running locally in the browser from a streamed session that needs a remote GPU and network. Neither is a transparent fallback for the other. Use the experimental Web target only when the brief permits a preview and the required browsers and delivery limits are compatible.

- For **Preview 2**, the [dated release notes](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-5-9-release-notes) supersede the Preview 1 C++ workaround still present in the [Web packaging guide](https://dev.epicgames.com/documentation/unreal-engine/packaging-your-project-for-webassembly?lang=en-US): a Blueprint-only project can package as-is. The engine still requires its matching Emscripten SDK. The guide documents a Windows build host, the Visual Studio C++ workload, emsdk 6.0.10 and Chrome as the reference browser. Verify the SDK against the actual build using Platforms > SDK Management or `RunUAT.bat Turnkey -command=VerifySdk -platform=Wasm`; do not assume "latest" is compatible.
- Preview 2 emits **wasm64** and requires **WebGPU**. Start with Epic's supplied development server on localhost. On a separate HTTPS host, send `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` on `index.html` and `sw.js`, and `Cross-Origin-Resource-Policy: same-origin` on all game files, along with the correct content types. If startup says the page is not isolated, inspect the actual response headers and check `window.crossOriginIsolated` before changing game code.
- Base a custom host on the matching engine's `Engine/Platforms/Wasm/Build/Tools/deploy/templates`. Check that the largest staged file fits, a range request to a game data file returns HTTP `206` with the exact requested raw bytes (no on-the-fly compression), and responses send `Cache-Control: no-cache` so the game's hash-based cache can revalidate. A full-file `200` or a working landing page is not this test.
- Cold-load in the target browser with its real device policies, check adapter and memory64 support, play the interaction, and measure transfer size, time to input and frame pacing. If offline use is promised, also test a disconnected relaunch under the promised installation/cache conditions. An editor preview, a successful cook or a PWA manifest proves none of these.
- For a WebGL2-only fleet or a first launch offline from a single file, don't promise this export. Keep a viable existing web stack or offer a smaller compatible slice. Consider streaming only if the owner accepts the changed connectivity, hosting and cost requirements.
