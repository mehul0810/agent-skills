# WordPress.org Listing Optimization

Use this mode to improve the usefulness and discoverability of a plugin's WordPress.org directory listing. It covers directory-specific positioning and copy, not a broad SEO campaign. For editing or validating the actual `readme.txt`, also load [readme-product-docs.md](readme-product-docs.md) and follow its release/package truth contract.

## Evidence And Search Intent

- Establish the plugin slug, current public listing, intended audience, established product positioning, and the exact currently shipped capabilities. Preserve the slug, plugin name, brand voice, and unrelated metadata unless a correction is explicitly requested and supported.
- Map plausible user problems and search phrases to verified capabilities. Use product documentation, support questions, and a bounded sample of current directory/search results when available. Record the query, date, locale, source, and limits of any observed search results; treat them as qualitative evidence, not comprehensive demand data.
- Do not invent search volume, ranking factors, competitor performance, conversion rates, or a causal explanation for visibility. If current search evidence is unavailable, label query ideas as hypotheses and proceed with user-problem language grounded in the product.
- Keep three outcomes distinct: WordPress.org directory discovery, Google/web search visibility, and listing-visitor-to-install conversion. Improving copy may help clarity and relevance; it does not guarantee rankings or installs.

## Listing Copy And Metadata

- Lead with the intended user/problem and the specific, verifiable job the plugin does. Describe concrete benefits only where the underlying capability and user outcome are evidenced. Avoid keyword repetition, generic superlatives, and unsupported superiority or compatibility claims.
- Keep the readme short description at or below 150 characters, plain text, and understandable on its own. Confirm character count after the final edit.
- Choose no more than five relevant directory tags. Use terms that accurately describe the plugin and its audience, including verified integrations where relevant. Do not hijack competitor names or stuff synonyms and unrelated high-volume terms.
- Make description sections, feature lists, setup steps, FAQs, and screenshot captions answer real user questions and match the current shipped product and UI. Do not add sections or claims merely to place keywords.
- State free versus paid functionality, required accounts, external services, data sent, material limitations, and setup dependencies plainly wherever relevant. Reuse the evidence and disclosure requirements in `readme-product-docs.md`; do not soften them for conversion.
- Optimize relevant tags and short-description metadata when listing improvement is in scope. Preserve the established name, slug, and brand; do not change those, release/technical metadata, or unrelated listing information as a side effect of copy optimization.

## Review And Measurement

- Check the result against the current official [Detailed Plugin Guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/) and [How Your Readme.txt Works](https://developer.wordpress.org/plugins/wordpress-org/how-your-readme-txt-works/). Consult the official readme validator when a file is written; do not infer policy from third-party SEO advice.
- Before/after notes may capture dated query set, locale, observed listing/search position when reproducibly available, listing content, and install/conversion measures only when the user provides trustworthy data. Keep comparisons like-for-like and record unavailable fields as unavailable.
- A baseline and later observation show sequence, not causation. Do not attribute ranking, traffic, or install changes to copy edits without a suitable controlled analysis.
- Editing or validating copy does not authorize SVN changes, directory submission, release, or publication. Report recommendations separately from edits and leave publication to the applicable release/owner approval.
