# Public skills: what to borrow, what to keep separate

Review date: 2026-11-22. Compared the nine upstream repositories below with the 16 existing skill entry points, their relevant design, documentation, graph and context references, the installer and its tests. The linked upstream files are pinned to the reviewed revisions. They are sources for design decisions, not dependencies or endorsements.

## Repository decision

**One public skill collection, not one repository for the entire agent system.** A newcomer should be able to select, install and try a skill from this repository without gaining access to any private repository. The public `agent-harness` is executable software with separate consumers and a versioned contract. A documentation update should not silently replace their validator. The existing [repository map](../README.md#repository-map) identifies the private responsibilities: live coordination, shadow decisions, and retained decision evidence. They need neither public disclosure nor a shared release cycle to improve skill discovery.

The tradeoff is real: changes spanning these boundaries may need more than one review and a tested dependency-pin update. Revisit the narrow Loop/Decide split if change history shows recurring lockstep releases, the same access and rollback needs, and a verified consumer inventory supports a compatible migration. One currently identified consumer is not proof that no others exist. Don't move private history, merge repositories, change visibility, or establish a new plugin or license to solve onboarding.

## What shipped in the patch

- One task-oriented [catalog and quick start](../README.md#skills), selective read-only verification for both supported install targets, and a [worked example with editable source](../examples/decision-flow/README.md). Selected installation still links shared resources in both roots. No third-party skill, code, asset, plugin, dependency, or model/effort setting was imported or changed.
- One [explanatory-diagrams skill](../explanatory-diagrams/SKILL.md). Its output is an editable explanation with source-supported connections and an equivalent short text. It does not own page creation, release documentation, inferred dependency maps, or proof of a running system. It can be installed separately and has no dependency on a private repo.
- GitHub listed the skills repository as public. The reviewed tree contains no root license file, and GitHub's repository-license endpoint returned 404. This patch does not select redistribution terms or claim an open-source license; that is an owner decision.

## Evidence and limits

**First use.** A fresh reader used the public quick start with an existing clone and two absent, disposable host roots. Installing and checking only `explanatory-diagrams` both exited zero. Each root gained the named skill, `shared`, and `templates`; neither gained a policy file or another skill. The reader had to open the skill to confirm it could *repair* a diagram; the catalog now says this directly. This is filesystem and discovery-guide proof, not observation of either app auto-loading a skill.

**Diagram exercise.** Two fresh performers used the same frozen [museum hold request](cases/explanatory-diagrams/input.json) and source artifacts, through separately installed skill paths. The performer packets excluded the [rubric](cases/explanatory-diagrams/criteria.md) and each other's material. Both produced editable SVG, matching help text, and an exact footer edit. Neither performer succeeded in rendering in its own context. Separately, an offline Chromium 153 browser produced actual 340- and 680-CSS-pixel renders; separate scorers inspected the images against the raw inputs.
