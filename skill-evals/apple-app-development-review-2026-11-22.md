# Apple app development and dependency selection

## Research decisions

Primary sources reviewed on 2026-11-22. Adopt an idea only where it changes a decision the installed skills make. No third-party skill, executable, hooks, telemetry, hosted service, or package dependency was added.

| Source | Fit for this agent system |
|---|---|
| [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) | Adopt the test for whether an existing implementation is enough, not a line-count target. The shared production-dependency guidance now contrasts a date input with a server-enforced booking rule: reuse the former without deleting the latter. |
| [ast-grep/ast-grep](https://github.com/ast-grep/ast-grep) | Useful for searching a code shape instead of reading many false text matches. The existing [research route](../shared/references/research-token-discipline.md) already supports this when installed. No second rule or mandatory install. |
| [rtk-ai/rtk](https://github.com/rtk-ai/rtk) | Structured summaries can avoid reading a whole command transcript. The [existing harness route](../shared/references/context-window-discipline.md) already supports recoverable bounded logs. For Xcode, query the native result bundle and retain the producer's status and full private log. Do not intercept shell commands. |
| [AvdLee/SwiftUI-Agent-Skill](https://github.com/AvdLee/SwiftUI-Agent-Skill) and [apple/sample-food-truck](https://github.com/apple/sample-food-truck) | Use the distinction between expensive and frequent updates, and platform-specific presentations over a shared model. Verify with [Apple's Instruments guidance](https://developer.apple.com/documentation/Xcode/understanding-and-improving-swiftui-performance) and the device HIG. Neither an upstream skill nor an older sample sets a product's deployment floor. |
| [swiftlang/swift-testing](https://github.com/swiftlang/swift-testing) | Use the testing support in a compatible toolchain for new logic tests. Preserve existing XCTest tests and use UI automation for user interaction; no external test library is needed for the native exercise. |
| [getsentry/MobileBuildMCP](https://github.com/getsentry/MobileBuildMCP) | An optional adapter for repeated iOS/macOS work, not a prerequisite. Upstream documents macro-validation and telemetry behavior; stock Xcode tools cover discovery, building, testing and result retrieval without changing trust. Reconsider only for a measured missing capability under the project's constraints. |

The new skill owns a **runnable Apple app**: device/OS floor, native input, framework compatibility, Xcode destination, and privacy/distribution boundaries. The existing Figma integration owns editable designs, WordPress skills own websites, and the game skill owns gameplay. No scheduling change in agent-loop, new decision engine in agent-decide, global model policy, or change to the pinned harness is necessary. These choices are not measured token, time, or cost savings.

## Native and command evidence

A separate builder made a dependency-free SwiftUI iPhone app and an XCTest UI test in a disposable project. The test used the actual buttons to go from 0 to 1 to 2, terminated and relaunched to observe 2, reset to 0, and relaunched to observe 0. The first log reported success but its shell wrapper lost the producer status. A fresh result bundle and correctly captured exit 0 confirmed **1 passed, 0 failed, 0 skipped** on an iPhone 17 simulator, iOS 26.5, with Xcode 27.0. One screenshot attempt after shutdown did not produce a screenshot. No manual visual, hardware, accessibility-conformance, signing, or store proof is claimed.

A different verifier used the recovery packet and skill with the same four source/project/test files (manifest SHA-256 `ce604b81a669a11b21787eed462513ae291da9abd89ddb64571501a9e0b580ca`), no prior output, and a different disposable simulator. The verifier's first wrapper also lost exit status; the separately retained rerun recorded exit 0 and **1 passed, 0 failed, 0 skipped** on iPhone 17 / iOS 26.5. Source hashes matched before and after. Both task-created simulators were removed; neither run exercised other hardware. macOS VoiceOver and narration were excluded by owner direction, not passed.

For that rerun the retained build/test log was **14,749 bytes** and the native JSON summary **1,004 bytes**. The smaller view preserved outcome, counts and destination; it does not replace the log, and this one comparison did not measure tokens or end-to-end savings. The documented command example was also exercised with four synthetic producer/reader status combinations in each of Bash and zsh, including a failed producer with a successful reader. All eight returned the expected status.

Both native wrappers independently chose the read-only zsh variable `status` rather than the example's `build_status`, costing each a rerun. The Xcode reference now names the pitfall and asks agents adapting the wrapper to exercise a cheap failure first. Its exact command block was tested with permissive starting permissions in Bash and zsh: all eight producer/reader combinations retained the original diagnostic, returned the expected status, and created a `0600` log and `0700` fixture bundle directory.
