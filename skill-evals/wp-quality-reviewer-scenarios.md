# WP Quality Reviewer Scenarios

| Scenario | Prompt | Expected behavior |
|---|---|---|
| Security review and fix | "Review and fix this plugin REST mutation for enterprise security." | Selects the security mode; maps actor, object, trust boundary, and source-to-sink path; reports evidence-backed findings; fixes server-side authorization and validation; adds wrong-role/wrong-object/malformed-input negative tests; avoids public exploit details; does not claim comprehensive security. |
| Performance review and fix | "This admin report is slow with 500k records. Find and fix the cause." | Selects performance mode; establishes revision, realistic dataset, cache state, baseline, and budget; proves the dominant query/cost; applies a bounded structural fix; remeasures comparable before/after values; does not use a tool score as proof of production capacity. |
| Performance tail, overload, and cache proof | "Prove this high-traffic export is safe after the optimization." | Defines request/item/concurrency/time/retry/queue/cost limits; captures repeated comparable runs with distribution, variance, error rate, cache state, provenance, and field/lab limits; proves over-limit behavior, dependency fallback, no retry storm, bounded backlog, and read-after-write or invalidation behavior when cached; does not claim capacity from a median or Lighthouse score alone. |
| Capacity envelope and scale lifecycle | "Assess a multi-tenant plugin that processes imports and queues while traffic and data are expected to triple." | Selects performance mode; records workload mix, cardinality, growth horizon, budgets, headroom, saturation trigger, tenant fairness/admission, queue arrival/service and drain behavior, storage/restore lifecycle, distributed failure handling, provenance, and limitations; uses `Not applicable - reason` only for genuinely irrelevant dimensions; does not invent universal thresholds or claim capacity from one median or green command. |
| Security authorization matrix and abuse budget | "Review this public REST bulk action used by multiple sites and fix any security gaps." | Produces an actor/action/resource authorization matrix with expected and observed decisions; verifies object/property/function-level authorization, multisite isolation, quantitative payload/batch/concurrency/time/retry limits, bounded 429/rejection/backoff and dependency failure behavior; keeps public disclosure sanitized and does not treat platform rate limits as application controls. |
| Modular refactor | "Review this plugin for duplicate code and poor boundaries, then refactor safely." | Selects modularity mode; maps WordPress entry points to business/persistence owners; distinguishes harmful duplication from intentional similarity; adds characterization proof; applies the smallest boundary change; preserves public hooks/data; stops before framework or abstraction bloat. |
| Legacy modularity ratchet and adapter boundary | "Add provider behavior requested by issue #81 to a 9,240-line legacy plugin file. The repo checker flags the file, but CI has no reusable modularity policy yet." | Does not rewrite the whole legacy file or waive the finding. Applies the changed-file no-growth ratchet, captures file/method baseline and characterization proof, puts new behavior behind a narrow inward-facing port with an outward provider adapter, checks dependency direction and cycles, and reports the threshold disposition. Keeps executable counters, path inventory, language extensions, baseline, and justified exception registry in the product repo; any exception names owner, issue/target, measured and allowed budget, and reduction or no-growth posture. |
| Non-breaking launched-contract refactor | "Refactor this launched REST and block feature for better modularity without breaking existing consumers." | Inventories hooks/routes/block attributes/saved markup and real data, captures characterization or consumer proof, extracts behind the existing public boundary, compares defaults/errors/side effects/permissions across reachable entry points, and reports an explicit compatibility result; it does not add shims for abandoned unreleased shapes or silently change a public contract. |
| Additive custom-table migration | "Split this custom-table repository and rename a column without breaking existing installs." | Treats the schema as a launched contract; uses additive expand -> migrate/backfill -> contract sequencing with resumable/rollback-safe behavior, compatibility reads or versioned writes where needed, migration/idempotency/upgrade tests, and a deferred cleanup plan. It does not delete or rename the live column in the first migration or claim safety from unit tests alone. |
| Accessibility remediation | "Audit and fix this block editor sidebar and modal for WCAG 2.2 AA." | Selects accessibility mode; reviews editor states, semantics, keyboard/focus, names/errors, reflow, contrast, and assistive technology; fixes native semantics before ARIA; requires keyboard and named screen-reader/browser proof; treats an automated scan as incomplete evidence. |
| Multi-domain release audit | "Before release, review security, performance, modularity, and accessibility and fix release blockers." | Binds an immutable commit/package identity, uses the compact multi-domain reference, and loads at most one detailed mode for a confirmed risk; records all four domain dispositions; blocks pass on unresolved P0/P1, proof gaps, incomplete domains, or a critical fix without fresh source-aware re-review; uses optional scanners only as evidence. |
| Feature versus review routing | "Build a new plugin settings screen with secure and accessible code." | `wp-plugin-expert` owns feature delivery and routine quality. It does not route to the reviewer unless a focused audit/remediation or independent reassessment is requested. |
| Contradicted pass | "You said the dialog passed, but this keyboard recording shows focus is trapped." | Reopens the exact accessibility clause, marks prior proof invalid, finds and fixes the cause, reruns the failed journey, and records a repeatable regression lesson instead of apologizing and preserving the pass. |
| Formal report validation | "Produce a release-critical multi-domain quality report." | Uses `wp-quality-review.schema.json`, immutable candidate identity, complete domain dispositions, scope/proof gaps, structured evidence and validation receipts, direction-and-budget performance measurements with tail/provenance fields when elevated, authorization/resource receipts when flagged, and exact-commit independent re-review for critical fixes; runs the deterministic validator before reporting pass. |
| Fabricated evidence rejection | "Validate this report: evidence says trust me, validation says passed." | Rejects free-form or vague proof, requires a concrete evidence locator and observation, and refuses a fixed/pass disposition until mode-proportionate structured receipts prove the original failure clause. |
