# Game development scoring

Score decisions against the constraints, not a prescribed brand of engine. Keep these criteria and prior results out of the evaluator packet.

| Case | Required distinction |
|---|---|
| 1. Fixed camera | Choose a feasible offline, GPU-independent interaction with an actual objective, input, result and retry. Preserve photographic detail with cleared imagery; check final bytes, touch and the exported build on the kiosk. |
| 2. Free movement | Reuse the viable native pipeline. Build a playable survey action with true depth, collision, moving light and differentiated surface response. Verify in motion at player scale; do not substitute a slideshow, trailer or engine migration. |
| 3. Mobile browser | Choose a concrete browser-capable 3D pipeline for the known devices and skills. Prove the WebGL path, touch orbit/parallax and asset/load cost on the intended device; neither fixed plates nor WebGPU-only rendering meet these requirements. |
| 4. Cartoon drift | Correct scale/contact, distinguish material response, match stride to travel and sound to surface. Test under representative light and movement; retain the useful accessible HUD cue rather than applying a global desaturation filter. |
| 5. Pacing and proof | Separate screenshot, editor and packaged handheld evidence. Identify the tail exceeding the roughly 16.7 ms frame budget, profile a repeatable busy traversal on target, change the measured bottleneck, and run the full loop. Do not claim success from the median. |
| 6. Restraint | Preserve the approved world and stack; fix/replay the input interruption narrowly. A trailer-only job is not playable game development. |
| 7. Rights and scope | Do not ship the restricted model or invent equivalent rights. Offer a cleared/original asset or an explicitly limited mechanic slice; separate placeholder, delivered content, and full eight-car acceptance. |
| 8. No supplied hero art | Produce suitable original art within the same request rather than waiting for the owner, polishing the UI or declaring the graybox final. Separate the live crown and hit area from the locked view. Check input, visible motion/feedback, alignment and replay in the actual build; report any unresolved visual gap. |

For the separate playable pilot, run the brief in the sibling `game-development-slice` case with the same frozen skill. Verify a clean local launch, interactive progress, completion, reset and output size; inspect the actual player view. Keep playability, photographic resemblance, and target-device performance as separate results. Do not promote a synthetic pilot to a production benchmark.

The sibling `game-development-plate` case supplies an original synthetic art asset. Inspect the rendered result beside that exact asset: the live scale and moving needle must fit the glass face, and pointer input must work on the pictured knob, not an unrelated slider beside a static photograph. Play through miss, success and restart. Do not pool this asset-assisted result with the no-asset pilot or treat it as evidence of navigable 3D realism.
