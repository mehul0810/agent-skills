# Game development: first-pass review

## What the research changed

Reviewed primary sources on 2026-11-20. These are design decisions for the skill, not a claim that one engine, frame rate or visual style is best for every game.

| Source | Decision for a one-request build |
|---|---|
| The Astronauts' accounts of [environment capture](https://www.theastronauts.com/2014/03/visual-revolution-vanishing-ethan-carter/) and [in-game foliage](https://www.theastronauts.com/2014/02/approached-3d-foliage-vanishing-ethan-carter/) | Use real-world scale and material evidence; concentrate detail where a player approaches. A more complicated effect can make the image look less natural in motion. |
| [Khronos glTF materials](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html) and [Epic's material inputs](https://dev.epicgames.com/documentation/en-us/unreal-engine/physically-based-materials-in-unreal-engine) | Don't fix a plastic-looking bench by adding dirt or raising resolution. Check which surface is painted, how its highlight spreads, and how the runtime interprets color versus data maps. |
| Epic on [pose warping](https://dev.epicgames.com/documentation/unreal-engine/pose-warping-in-unreal-engine) and [sound attenuation](https://dev.epicgames.com/documentation/en-us/unreal-engine/sound-attenuation-in-unreal-engine) | Match contact to travel and feedback to the event, material and listener. Play the action rather than rating a still or requiring these specific engine features. |
| [Godot renderer differences](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html), [Unity pipeline choice](https://docs.unity3d.com/Manual/choose-a-render-pipeline.html) and [Unreal lighting scalability](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-performance-guide-for-unreal-engine) | Choose for the weakest target, necessary camera freedom, team pipeline and budget. A renderer's best-looking example is not proof that the game can ship on that device. |
| Android's [frame pacing](https://developer.android.com/games/sdk/frame-pacing) and [thermal guidance](https://developer.android.com/games/optimize/adpf) | Check the spread of frame times on a repeatable busy route, including sustained play when relevant. Do not infer smooth play from a good average or a desktop screenshot. |

## Admission and test scope

No existing skill in this pack owned the playable loop, choice of runtime, interactive visual proof and game-specific handoff. Existing image and video workflows can supply supporting media, not the game. No WordPress router, engine dependency, model, reasoning limit or global design default changed.

The blind cases under `skill-evals/cases/` separate stack and art decisions (`game-development`), a small offline build (`game-development-slice`), and an art-assisted build (`game-development-plate`). The evaluator inputs and scoring criteria are separate. Candidate skills and requests were frozen in disposable Git snapshots; tree IDs below identify the skill bytes, not the publication commit. This is development evaluation, not a held-out benchmark.

**Art-assisted condition.** Same skill tree, different input. An original generated 1536 x 1024 image of an unbranded instrument was made specifically for this experiment; it is not a photograph of a real object. Its face was left blank so the game, not the image generator, could own the scale, needle, and response. The JPEG in the packet is 359,678 bytes, SHA-256 `15c5f4a690e71a30fdeecbdb3a90bc94f1bdb3cf50abfb6447f960cb0657995c`; packet manifest SHA-256 `cdf37744813df34b48e2791697ef0472b1678dbc11a4cec8f8becbae105c94f5`. This tests assembling a game from a suitable original asset, not generating comparable art from code alone.

The builder used plain HTML, SVG and JavaScript, embedded the JPEG, and corrected the printed scale, needle reach and center tolerance during review. The final file was 487,315 bytes, SHA-256 `be05564d75999fe214ea58e55cd7a485f02a61282b6e2e5773bfffab1d473ed2`. In an independent offline Chrome 158 session, the first submit missed, dragging the pictured knob moved the rendered needle and passed, and Tab plus arrow keys and Enter passed a new calibration after resizing. The game reset for a third round. No page errors or external requests were observed. Captures at 1280 x 900 and the input check at 940 x 720 are desktop evidence, not mobile or frame-pacing measurements. The trim readout is the applied correction, not the remaining error; the result is scored on submit.

The supplied-art case retained the casing, reflected daylight, paper, glass and bench grain while the live components moved. The no-asset case did not achieve the same visual result. Neither proves a navigable 3D environment, sustained target-hardware performance, or repeatable one-shot production quality. Local run bundle: `bench-zero-game-development-20261120`, including the playable file, independent play result, captures and separate attempts.
