# UI and UX source atlas

Use this as a reading shelf, not a checklist. Open the source that answers the current design decision. A studio account describes its own project; a tutorial teaches a technique; a usability method tells you how to investigate. None establishes that copying an effect will help your audience.

**Start with the question:**

- **How do I make this feel like this brand?** Start with Hello Monday (57) for translating a physical experience, Instrument (55) for preserving an identifiable element, or AREA 17 (62) for an exhibition and its editorial system. Ask what relationship should recur after both the headline and image change.
- **Where do the little details belong?** The [four-site study](../skill-evals/product-site-design-study-2026-11-23.md) names Jetpack's hairline rules, registration marks, hatched dividers and outline wordmark. Compare them with the Intrepid Museum's logo-derived hover cue (71). Give the detail one job: align a row, mark a section change, or acknowledge an action. If removing it makes the action unintelligible, fix the label or hierarchy; if it looks clickable but does nothing, simplify it.
- **How do I actually build it?** Read Ahmad Shadeed on the space available to a component, Every Layout on an intrinsic sidebar, or Utopia on bounded type scales. Try the technique on the same content in two different host widths before changing the whole layout.
- **Can people find the next step?** Compare Maze on writing a task with Optimal Workshop on testing a navigation tree. A text tree tests labels and grouping without the page styling. The rendered page also brings in layout, menu disclosure and surrounding content. A difference is a clue, not proof of its cause; doing the task twice can teach someone the answer. The [worked theatre example](navigation-study-worked-example.md) shows how to follow through to the real action.
- **What happens when the design meets real data?** Compare Elastic on reasons a panel is empty, GOV.UK on retaining answers after errors, and The Markup on explaining an illustration without depending on the image. Test the actual missing, invalid or long-content case.

**Browse:** [Design systems](#design-systems) · [Research and design practice](#research-and-design-practice) · [Studio case studies](#studio-case-studies) · [Frontend craft](#frontend-craft).

**Scope on 2026-11-23:** 110 counted websites, one substantive, readable public page per entry. Known shared operators and aliases were consolidated; the count is not an audit of ultimate corporate ownership. We excluded unreadable, snippet-only and archived or duplicate candidates. Older sources are identified by their linked publication; verify current browser or framework support before adopting an example. We did not run all 110 interfaces, verify the studios' reported results, or reproduce their assets.

For a visual starting point only, [Siteinspire’s typographic collection](https://www.siteinspire.com/websites/category/typographic) and [One Page Love’s collection note](https://onepagelove.com/collected) are useful **uncounted** discovery shelves. Follow a candidate to its original site or case study before attributing behavior.

## Design systems

| # | Source | What the documented pattern shows | What to try |
| ---: | --- | --- | --- |
| 1 | [Carbon: Form](<https://www.carbondesignsystem.com/building-blocks/core/components/form/accessibility>) | The form guidance describes inline errors and programmatic error states. | Specify both visible and programmatic error states for each form control. |
| 2 | [Spectrum: Writing for errors](<https://spectrum.adobe.com/page/writing-for-errors/>) | Spectrum says to choose an error component after considering the message, trigger, context, and user activity. | Draft the error and identify its context before selecting its presentation component. |
| 3 | [GOV.UK Design System: Error message](<https://design-system.service.gov.uk/components/error-message/>) | GOV.UK says to retain passing and failing answers when displaying validation errors. | Preserve submitted values while users correct invalid fields. |
| 4 | [U.S. Web Design System: Modal](<https://designsystem.digital.gov/components/modal/>) | USWDS recommends contextual field errors instead of modal messages and cautions against complex modal content. | Prefer in-context validation and reserve dialogs for decisions that justify interruption. |
| 5 | [Primer: Forms](<https://primer.style/product/ui-patterns/forms/>) | Primer advises waiting until users finish an initially valid field before validating it. | Define validation timing so incomplete typing is not immediately treated as an error. |
| 6 | [Pajamas: Forms](<https://design.gitlab.com/patterns/forms/>) | Pajamas says the clear control should be keyboard operable and return focus to the input. | Specify focus restoration when a clear action changes an input. |
| 7 | [Elastic UI: Empty prompt](<https://eui.elastic.co/v106.6.0/docs/components/display/empty-prompt/>) | Elastic distinguishes first use, missing privileges, no results, loading errors, and loading as separate scenarios. | Map each absence scenario to its own explanation and next action. |
| 8 | [eBay Playbook: Error States](<https://playbook.ebay.com/design-system/patterns/error-states>) | eBay distinguishes an inline field error from failures of the system and missing content. | Define separate recovery copy for invalid input, missing content, and system failure. |
| 9 | [Garden: Color](<https://garden.zendesk.com/design/color/>) | Garden separates actionable primary color from semantic success, warning, and danger colors. | Define semantic color roles separately from interactive emphasis and pair status with non-color cues. |
| 10 | [Ontario Design System: Error messaging](<https://designsystem.ontario.ca/components/detail/error-messaging.html>) | Ontario says not to clear form fields after an error and not to hide errors in tooltips. | Keep error text visible and retain previously entered data after validation fails. |
| 11 | [GC Design System: Error summary - Design](<https://design-system.canada.ca/en/components/error-summary/design/>) | The GC summary lists errors in form order, links each item to its context, and matches inline wording. | Keep summary order and wording synchronized with the form and its inline errors. |
| 12 | [Designsystemet: User-triggered error messages](<https://designsystemet.no/en/patterns/errors>) | Designsystemet discourages disabled submit buttons as a form-validation mechanism. | Allow a submission attempt and explain what must be corrected when validation fails. |
| 13 | [Queensland Government Design System: Forms overview](<https://www.designsystem.qld.gov.au/components/forms/tabs/overview>) | Queensland demonstrates a field associating both hint and error text with its input. | Connect relevant hints and errors to their field in the accessible description. |
| 14 | [Skyline: Form Error Handling](<https://skyline.benevity.org/design/patterns/form-error-pattern/>) | Skyline uses a form-level error alert for failures that are not tied to a particular field, such as a connection problem. | Provide a distinct form-level recovery message for submission failures outside field validation. |
| 15 | [UL Design System: Empty State](<https://designsystem.ul.com/components-v2/empty-state/>) | UL allows an empty state to sit near the task that resolves it rather than always centering it. | Place the empty-state action where its relationship to the affected task is clear. |
| 16 | [Nord Design System: Empty State](<https://nordhealth.design/components/empty-state/>) | Nord asks empty-state headings to explain why content is absent and action labels to predict the result. | Replace generic empty-state headings and buttons with the reason and a specific next step. |
| 17 | [Constellation: Empty state](<https://design.pega.com/versions/8/design/empty-state/index.html>) | Pega documents empty states for data that is absent or has yet to appear, with optional actions or progress. | Choose an action or progress cue based on why the data region is empty. |
| 18 | [New York State Design System: Build an Accessible Modal Dialog](<https://designsystem.ny.gov/components/modal/accessibility-build/>) | New York State discusses a native modal dialog alternative and its focus, inertness, and responsive behavior. | Assess native dialog behavior and integration requirements before creating custom modal machinery. |
| 19 | [Singapore Government Design System: Modal](<https://designsystem.tech.gov.sg/components/modal>) | Singapore documents moving focus to the modal heading on open and restoring it to the trigger on close. | Specify initial and return focus for every modal interaction. |
| 20 | [Kolibri Design System: Modals](<https://design-system.learningequality.org/modals/>) | Kolibri places validation errors inside the active modal and advises against stacked modals. | Keep modal validation in context and avoid requiring a second modal to resolve it. |
| 21 | [Telerik Design System Kit: Notification usage](<https://www.telerik.com/design-system/docs/components/notification/usage/>) | Telerik says notifications should not cover important content and discourages multiple messages that can be merged. | Group related notices and check that their placement does not obscure active controls. |
| 22 | [Maersk Design System: Notification](<https://designsystem.maersk.com/components/notification/index.html>) | Maersk distinguishes global notifications for whole-page issues from inline notifications. | Scope notifications to the affected region and offer an action where resolution is possible. |

## Research and design practice

| # | Source | What the method shows | What to try |
| ---: | --- | --- | --- |
| 23 | [Nielsen Norman Group: Memory Recognition and Recall in User Interfaces](<https://www.nngroup.com/articles/recognition-and-recall/>) | It contrasts recognizing visible options with retrieving commands from memory, including interface cues and recent searches. | Keep previously available choices or meaningful labels in view when a visitor would otherwise have to remember them. |
| 24 | [Baymard Institute: What Is an Ecommerce Filter? UI Best Practices](<https://baymard.com/blog/ecommerce-filter-ui>) | The article shows how hiding active filters inside a closed mobile panel makes the current result set harder to interpret. | Place a removable summary of active constraints beside the results, not only inside the filter panel. |
| 25 | [Design Council: Framework for Innovation](<https://www.designcouncil.org.uk/resources/framework-for-innovation/>) | The first diamond investigates and defines the problem before the second explores and tests possible responses. | If alternatives all restyle the same mistaken problem, revisit a real visitor task before drawing more screens. |
| 26 | [IDEO.org Design Kit: How Might We](<https://www.designkit.org/methods/how-might-we.html>) | The method tests whether a question permits more than one solution while remaining narrow enough to design for. | Frame why visitors lose their place, not how to add a sticky bar; different solutions can then compete. |
| 27 | [LUMA Institute: Creative Matrix](<https://www.luma-institute.com/creative-matrix/>) | The method places distinct categories on two axes and asks for ideas at their intersections. | When ideas converge too early, cross a real visitor task with a relevant physical or editorial cue and sketch a plausible intersection. |
| 28 | [W3C WAI: Page Structure Tutorial](<https://www.w3.org/WAI/tutorials/page-structure/>) | The tutorial distinguishes named regions from the headings that express relationships inside them. | Check that the document outline still describes the page when visual tile boundaries disappear. |
| 29 | [WebAIM: Cognitive Disabilities: Design Considerations](<https://webaim.org/articles/cognitive/design>) | Context reminders, meaningful groups and visual separation are proposed for readers managing cognitive load. | On a complex flow, show where someone is and what their current step requires instead of relying on remembered instructions. |
| 30 | [TetraLogical: Foundations: Pointer Gestures](<https://tetralogical.com/blog/2023/03/17/foundations-pointer-gestures/>) | The guide distinguishes path-dependent or multi-point gestures from simpler pointer actions and illustrates alternatives. | If a special gesture unlocks content, offer a visible tap or click that accomplishes the same task. |
| 31 | [Deque: How to Design Useful and Usable Focus Indicators](<https://www.deque.com/blog/give-site-focus-tips-designing-usable-focus-indicators/>) | It contrasts obvious focus cues with subtle or removed outlines across controls and surrounding colors. | Inspect focus on each actual surface, not only on the background used in the component sample. |
| 32 | [Liberating Structures: 1-2-4-All](<https://www.liberatingstructures.com/1-2-4-all>) | Ideas are developed individually, then in pairs and groups before everyone compares them. | For a facilitated ideation session, give individuals space to sketch before promoting the first group favorite. |
| 33 | [Product Talk: Assumption Testing](<https://www.producttalk.org/assumption-testing/>) | The author separates testing a risky assumption from testing an entire proposed solution. | Prototype the one uncertainty that could invalidate the direction, not every proposed page. |
| 34 | [Strategyzer: Validate Your Ideas with the Test Card](<https://www.strategyzer.com/library/validate-your-ideas-with-the-test-card>) | The test card separates belief, experiment, measurement and a predeclared decision threshold. | Decide what observation would disqualify a pattern before calling a friendly reaction validation. |
| 35 | [Balsamiq: Wireflows](<https://balsamiq.com/blog/wireflows/>) | Wireflows attach screen sketches to the actions that move the user between them. | Sketch the return and failure paths beside a novel interaction before investing in polished frames. |
| 36 | [Smashing Magazine: The Role of Empty States in User Onboarding](<https://www.smashingmagazine.com/2017/02/user-onboarding-empty-states-mobile-apps/>) | It treats a first-use empty screen as a place to teach the next action before the user's own content exists. | Choose a useful first action rather than presenting a dashboard full of zeros as a system failure. |
| 37 | [Design Justice Network: Read the Principles](<https://designjustice.org/read-the-principles>) | The network's principles prioritize people directly affected by a design and the effects they experience over designer intention. | Include the people who bear the cost of a confusing process when evaluating it; a designer's good intention is not evidence. |
| 38 | [Service Design Tools: Service Blueprint](<https://servicedesigntools.org/tools/service-blueprint>) | The blueprint separates the actions users see from the behind-the-scenes work that supports them. | Do not design a confirmation as complete before its operational handoff can actually be delivered. |
| 39 | [This Is Service Design Doing: Desktop Walkthrough](<https://www.thisisservicedesigndoing.com/methods/desktop-walkthrough>) | A tabletop enactment uses movable props to walk through a service with different actors and sequences. | For a multi-actor service, rehearse a handoff or interruption before spending time on high-fidelity UI. |
| 40 | [Storybook: Interaction Tests](<https://storybook.js.org/docs/writing-tests/interaction-testing>) | A story defines the initial component state; a play function exercises actions and asserts the result. | For a reusable stateful control, test the result from a meaningful starting state, not just a screenshot of the default. |
| 41 | [Figma: Multiple Actions and Conditionals](<https://help.figma.com/hc/en-us/articles/15253220891799-Multiple-actions-and-conditionals>) | The guide demonstrates ordered prototype actions and branches whose destinations depend on variables. | Prototype one meaningful branch if it changes a decision; label the mock as a prototype, not working persistence. |
| 42 | [Maze: Best Practices for Writing Tasks and Descriptions](<https://help.maze.co/articles/5769270783-best-practices-for-writing-tasks-and-descriptions>) | The task-writing guide separates the participant's goal from instructions that give away the route. | Describe the person's situation in their language and omit the interface's label or gesture from the test prompt. |
| 43 | [Optimal Workshop: Write Your Tasks](<https://www.optimalworkshop.com/101-guides/tree-testing-101/write-your-tasks>) | The tree-testing guide ties tasks to objectives and recommends covering multiple branches rather than repeatedly targeting one area. | Test competing plausible destinations with realistic tasks; success in a text hierarchy does not test the visual navigation. |
| 44 | [Center Centre: The Right Trigger Words](<https://articles.centercentre.com/trigger_words/>) | The author uses navigation examples to show the clues visitors look for in link wording. | Keep a recognizable noun from the visitor's problem in a destination label rather than relying on a clever slogan. |
| 45 | [LukeW: Testing Real Time Feedback in Web Forms](<https://www.lukew.com/ff/883/testing-real-time-feedback-in-web-forms>) | The author reports testing different timings and presentations for feedback while people fill in forms. | Check a partial entry, a completed invalid entry and a correction rather than assuming earlier interruption is always better. |
| 46 | [Content Design London: How to Work with User Needs](<https://contentdesign.london/blog/how-to-work-with-user-needs>) | The article starts with what a reader is trying to do rather than what an organization wants to publish. | Translate a business request into the reader's question before writing headings and navigation labels. |
| 47 | [Stark: Using Focus Order](<https://www.getstark.co/support/getting-started/establishing-focus-order/>) | The tool's guide illustrates explicit focus sequences and individual items as design annotations. | Annotate a non-obvious intended tab sequence, then test the actual build; the annotation cannot prove keyboard behavior. |
| 48 | [AbilityNet: Designing for Dementia](<https://abilitynet.org.uk/factsheets/designing-dementia>) | This guidance combines co-design with shorter text chunks, descriptive headings and clear organization. | For a complex task, check the reading order and clarity with affected users rather than merely increasing the type size. |
| 49 | [The A11Y Project: Creating Valid and Accessible Links](<https://www.a11yproject.com/posts/creating-valid-and-accessible-links/>) | The author compares ambiguous link labels with descriptions that still identify the destination outside their surrounding paragraph. | When cards repeat, ensure their links identify the actual item or destination, not just a shared action verb. |
| 50 | [Inclusive Design Guide: One-Size-Fits-One](<https://guide.inclusivedesign.ca/insights/one-size-fits-one/>) | The guide uses everyday adjustable objects to prompt designs that adapt to individuals rather than one presumed average. | When one presentation excludes part of the audience, evaluate a meaningful alternative without removing the core task. |
| 51 | [From Data to Viz: A Note on Long Labels](<https://www.data-to-viz.com/caveat/hard_label.html>) | A worked chart example shows how rotating long category labels makes them harder to read and compares a horizontal arrangement. | Try changing orientation before reducing text size or abbreviating the reader's category names. |
| 52 | [The Markup: How We Approach Visual Storytelling Accessibility at The Markup](<https://themarkup.org/hello-world/2023/09/16/how-we-approach-visual-storytelling-accessibility-at-the-markup>) | The newsroom describes considering accessibility while planning illustrations and visual stories rather than adding descriptions only at delivery. | Write the communicative purpose of an illustration early enough to guide both its composition and its text alternative. |
| 53 | [Service Design Show: How to Create a Customer Journey Map](<https://www.servicedesignshow.com/customer-journey/how-to-create-a-journey-map/>) | The worked exercise maps a customer's context and activities before adding needs to particular moments. | Distinguish what the visitor is trying to accomplish from what the organization wants the next screen to sell. |
| 54 | [Laws of UX: Aesthetic-Usability Effect](<https://lawsofux.com/aesthetic-usability-effect/>) | The author describes how visual appeal can disguise difficulty during a usability evaluation. | Record where people get stuck independently of whether they like the design. |
